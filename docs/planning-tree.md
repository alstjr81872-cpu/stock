# STEP 2: 공통 기획 트리

Cloudflare/Supabase 배포에서 STEP 2는 `큰 틀 잡기 → 가지 구체화 → 연결 검수` 순서로 진행합니다.
기존 Firebase/Python 로컬 어댑터는 보존된 상세 모듈 화면을 사용합니다.

## 사용 순서

1. 원문 분석 후 STEP 2에서 **큰 틀 잡기**를 누릅니다. 세계관·인물·스토리·문체를 연결한 기획과 공통 이름/배경을 제안받습니다.
2. 비용 확인 뒤 제안을 검토하고 **기획에 반영**합니다. 미리보기만으로 기존 데이터가 바뀌지 않습니다.
3. 왼쪽 트리에서 가지를 선택하고 **이 가지 구체화**로 하위 설정과 연결을 발전시킵니다. 오른쪽에서 관련 가지로 이동할 수 있습니다.
4. 미정·충돌의 **연결해서 해결**은 해당 문제 ID와 관련 기획을 모델에 전달합니다. 문장이 바뀌어도 같은 ID의 해결 근거를 기록합니다.
5. 공통 인물·장소·세력 등록부에서 이름을 바꾸면 ID 참조를 사용하는 트리 화면에서 함께 표시됩니다. 연결된 가지는 검토 필요로 바뀝니다.
6. **상세 모듈 보기**에서 공통 트리를 바탕으로 11개 문서를 정리하고, 기존 문체·교차 검토·작품 등록 절차를 진행합니다.

기존 모듈은 `module-*` 가지와 원래 문서로 보존됩니다. 원문 TXT와 요구사항을 삭제하거나 재업로드할 필요가 없습니다.
기존 자유 텍스트를 무조건 문자열 치환하지 않습니다. 오래된 문서는 변경 영향 표시를 확인하고 트리 기준으로 다듬거나 다시 생성하세요.
기존 상세 문서의 자동 기획 버튼은 편집을 저장한 뒤 대응하는 트리 가지로 이동합니다.

## 데이터와 검증

- `project.planningTree`: 노드, 공통 엔티티, ID 기반 문제와 결정 이력. 모든 노드에는 부모, 요구 근거, 대상/의존 연결이 있습니다.
- 부모 순환·존재하지 않는 연결·잘못된 원문 근거·중복 ID를 차단합니다. 새 패치에 없는 기존 가지/문제는 보존합니다.
- 문제 해결에는 resolution과 관련 노드 수정이 필요합니다. 기존 모듈 문제의 대응은 최초 가져오기 시 부여한 ID/출처 위치로 관리하며, 표현 일치로 해결을 판단하지 않습니다.
- 미리보기, 적용, 이름 변경은 인증된 계정에 귀속됩니다. revision CAS로 기획·제안 상태·변경 이력을 원자 저장합니다.
- 관련된 하위/의존 가지에 변경 영향을 전파하고 기존 플롯·교차 검토 승인을 무효화합니다. 원문 요구와 최종 사람의 승인 절차를 유지합니다.
- 독립 검토와 플롯/집필 입력에도 공통 트리를 전달합니다. 모델 입력에서 처리용 메타데이터를 제거하고 출력 스키마에 필요한 ID/연결을 유지합니다.
- 변경 이력과 프로젝트 ZIP에 트리 제안/이력이 포함됩니다. 새 SQL 또는 비밀 키 설정은 필요하지 않습니다.

현재 노드 160개·공통 대상 100개, 프로젝트 문서 전체 크기 제한이 적용됩니다. 실제 모델의 연결 품질과 Free Workers 처리 한도는 실제 배포에서 검수해야 합니다.
